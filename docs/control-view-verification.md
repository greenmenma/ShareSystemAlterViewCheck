# 制御テーブル切替ビュー　インデックス・副作用の検証

本命の「制御テーブル切替」で使う公開ビューについて、2026-11-13 に次の点を検証しました。

- 利用者の SELECT でインデックスが効くか
- 非公開側のテーブルを無駄に読まないか
- 切替と重なったときに、結果が重複したり欠けたりしないか
- ロック（切替・後片付け・投入・統計更新）と、推定行数・ログ量に問題がないか

全体の経緯と結論は [検証まとめ](lock-verification-summary.md) を参照してください。

## 1. 結論

| 項目 | 結果 |
| --- | --- |
| 旧ビュー（CROSS APPLY 版） | **インデックスが効かない**。主キーの 1 件検索でも、公開中の側を毎回全件スキャンしていた |
| 新ビュー（スカラーサブクエリ版）に変更 | 主キー・インデックスの Seek が効く。非公開側は通常読まない |
| 整合性 | **RCSI ON なら正しい**（重複・欠落なし）。RCSI OFF や `NOLOCK` では、切替と重なると重複・0 件が起きる |
| ロック | 切替・後から来た SELECT ともに待たない（旧ビューと同じ）。後片付けは、切替より後に始まった SELECT の終了も待つ |
| 注意が必要なクエリ | インデックスのない列での `ORDER BY`（並べ替え）は、非公開側にデータがある間だけ両側を読む |
| アプリでの再確認 | プリセット ⑧ を新ビューで実行し、切替 37ms／2ms、読み取りの待ち 10ms 以下、ログ合計 3.4MB で成功 |

アプリのビュー定義（`DbObjects.CreateCtlViewSql()`）は新ビューに変更済みです。検証サーバーでは「環境セットアップ」を実行し直すと新しい定義になります。

## 2. ビュー定義

### 新（採用）：スカラーサブクエリ版

```sql
CREATE VIEW vt_CtlView AS
SELECT Id, Code, Name, Amount, UpdatedAt, Payload FROM vt_Ctl_A
WHERE (SELECT ActiveSide FROM vt_CtlActive WHERE Id = 1) = 'A'
UNION ALL
SELECT Id, Code, Name, Amount, UpdatedAt, Payload FROM vt_Ctl_B
WHERE (SELECT ActiveSide FROM vt_CtlActive WHERE Id = 1) = 'B';
```

### 旧：CROSS APPLY 版

```sql
CREATE VIEW vt_CtlView AS
SELECT x.* FROM vt_CtlActive c
CROSS APPLY (
    SELECT … FROM vt_Ctl_A WHERE c.ActiveSide = 'A'
    UNION ALL
    SELECT … FROM vt_Ctl_B WHERE c.ActiveSide = 'B'
) x
WHERE c.Id = 1;
```

旧ビューでは、利用者の WHERE 条件が CROSS APPLY の内側まで押し込まれず、片側を全件読んでから絞り込んでいました。

比較のため、次の 2 つの書き方も検証しました。

| 名前 | 書き方 |
| --- | --- |
| EXISTS 版 | 各側に `WHERE EXISTS (SELECT 1 FROM vt_CtlActive WHERE Id = 1 AND ActiveSide = 'A')` |
| JOIN 版 | 各側を `vt_CtlActive c JOIN vt_Ctl_A a ON c.Id = 1 AND c.ActiveSide = 'A'` |
| CROSS APPLY 分割版 | 各側ごとに CROSS APPLY を書いて UNION ALL |

## 3. 検証環境

- Mac 上の SQL Server 2022 Developer（Docker）、復旧モデル SIMPLE、RCSI ON（ユーザー環境と同じ）
- A・B・退避用テーブルは、アプリと同じ列構成に、主キー（`Id`）と非クラスタ化インデックス（`Code`）を付けたもの。各 30 万行（約 150MB）
- クエリは `sp_executesql` で実行し（プランがキャッシュされる）、`SET STATISTICS IO` でテーブルごとの論理読み取りページ数を測定

## 4. インデックスと読み取りページ数

テーブルの状態ごとに、A・B それぞれの論理読み取りページ数を測りました。

### 投入〜切替の間（A 公開中・B にも 30 万行）

| クエリ | 旧 CROSS APPLY | EXISTS | JOIN | **新 スカラー** |
| --- | --- | --- | --- | --- |
| Q1 `WHERE Id = @p` | A=18,817 | A=3 B=3 | A=3 B=3 | **A=3 B=0** |
| Q2 `WHERE Code = @p` | A=18,817 | A=33 B=6 | A=33 | **A=33 B=0** |
| Q3 `TOP 10 … ORDER BY Id` | A=1,470 | A=3 B=3 | A=3 | **A=3 B=0** |
| Q4 別テーブルと `Code` で JOIN | A=1,470 | A=188 B=6 | A=152 | **A=188 B=0** |
| Q5 `GROUP BY Code` | A=1,470 | A=1,547 B=26 | A=1,547 | **A=1,547 B=0** |
| Q6 `TOP 100000 … ORDER BY Name`（索引なしの列） | A=18,817 | A=19,763 **B=19,763** | 同左 | A=19,763 **B=19,763** |
| Q7 `COUNT(*)` | A=1,470 | A=1,547 B=26 | A=1,547 | **A=1,547 B=0** |

- 旧ビューは、主キーの 1 件検索（Q1）でも全件スキャン（18,817 ページ）でした。
- 新ビューは、Q1〜Q5・Q7 で Seek または必要な範囲だけを読み、非公開側の B は 0 ページでした。実行計画では、制御テーブルを先に読み、値が一致しない側は実行されていません（Executes = 0）。
- 切替後（B 公開中・A に旧データが残っている状態）、後片付け後（A が空）も、A・B を入れ替えた同じ結果でした。

### 注意：インデックスのない列で並べ替えるクエリ（Q6）

どの書き方でも、**非公開側にデータがある間は、非公開側も全件読んで並べ替えていました**（旧ビューのみ、全件スキャン 1 回分で済む）。
SQL Server は、各側を並べ替えてから結合する（Merge Concatenation）実行計画を選びます。このとき制御テーブルの判定が並べ替えの後に置かれるため、非公開側の読み取りを省けません。

- 結果は正しく、待ちも発生しません。読み取りの量が増えるだけです。
- 非公開側にデータがあるのは「投入〜切替」と「切替〜後片付けの完了」の間だけです。後片付けが済めば非公開側は空になり、読み取りは 0 ページです。
- 対策：後片付けを確実に終わらせ、非公開側にデータが残る時間を短くします。よく使う並べ替えの列にはインデックスを用意します。

## 5. 切替と重なったときの整合性

切替（制御テーブルの UPDATE）を 3ms 間隔で 25 秒間繰り返しながら、`SELECT COUNT(*)` を 150 回ずつ実行しました。A・B とも 30 万行なので、正しい結果は常に 300,000 です。

| 条件 | 旧 CROSS APPLY | EXISTS | **新 スカラー** | 新 スカラー + `NOLOCK` |
| --- | --- | --- | --- | --- |
| RCSI ON | 全て 300,000 | 全て 300,000 | **全て 300,000** | 600,000（重複）が 9 回 |
| RCSI OFF | 全て 300,000 | 600,000 が 123 回、半端な件数も | 0 件が 1 回、600,000 が 3 回 | 600,000 が 137 回 |

- 新ビューは制御テーブルを A 側・B 側で 1 回ずつ読みます。**RCSI ON なら 1 文の中は同じスナップショットを読むので、両方が同じ値を見ます**。
- RCSI OFF（ロック方式の READ COMMITTED）では 2 回の読み取りの間に切替が入り得るため、両側を返す（重複）・どちらも返さない（0 件）ことがあります。
- `NOLOCK`（READ UNCOMMITTED）は RCSI ON でも重複が起きます。**公開ビューを `NOLOCK` で読む利用者がいないか確認してください。**
- 旧ビューは制御テーブルを 1 回しか読まないため RCSI OFF でも正しいですが、インデックスが効かないため採用しません。ユーザー環境は RCSI ON です。

## 6. ロック

### 重い SELECT 中の切替・後片付け（RCSI ON）

約 40 秒かかる重い SELECT（R1）の実行中に、次の操作を順に行いました。

| 開始 | 操作 | 所要時間 | 備考 |
| --- | --- | --- | --- |
| 0 秒 | R1：重い SELECT（切替前に開始） | 40.3 秒 | |
| 3 秒 | 制御テーブルを UPDATE（A → B） | **9ms** | 待ちなし |
| 5 秒 | 軽い SELECT（`Id` で 1 件） | **0ms** | 待ちなし |
| 6 秒 | 旧側 A の `UPDATE STATISTICS` | 130ms | 待ちなし（R1 が A を読み中でも可能） |
| 7 秒 | 後片付け：A を低優先度 SWITCH で退避 | **45.4 秒** | `LCK_M_SCH_M_LOW_PRIORITY` で待機 |
| 10 秒 | 軽い SELECT（`Code` で検索） | **0ms** | 後片付けが待機中でも止まらない |
| 12 秒 | R4：重い SELECT（**切替後に開始**） | 40.4 秒 | B だけを読む |

**後片付けは R1（約 40 秒後に終了）ではなく、R4 の終了（約 52 秒後）まで待ちました。**
ビューを読む SELECT は、読まない側も含めて A・B の両方に Sch-S を持ちます。そのため、切替後に始まった SELECT も後片付けを待たせます。
後片付けを実行できるのは、「公開ビューを読む SELECT が 1 本も実行されていない瞬間」です。重い SELECT が途切れずに重なり続ける環境では、後片付けが時間切れになることがあります（[検証まとめ 7 章](lock-verification-summary.md#7-本命の注意点) のとおり、次回の更新の最初に再度空にします）。

### 非公開側への投入中（未コミット）の読み取り

非公開側へ `INSERT … WITH (TABLOCK)` を実行し、コミットせずに 12 秒保持している間に、公開ビューを読みました。

| 条件 | 結果 |
| --- | --- |
| RCSI ON | どのクエリも待ちなし（Q6 の両側を読むクエリも 162ms で終了） |
| RCSI OFF | 非公開側に触れるクエリが、投入のコミットまで待たされた（例：9.5 秒） |

### 利用者の分離レベル

利用者がトランザクション内でビューを読み、そのまま 8 秒保持している間に切替（制御テーブルの UPDATE）を実行しました。

| 利用者の分離レベル | 切替の待ち |
| --- | --- |
| READ COMMITTED（RCSI ON・既定） | なし |
| SNAPSHOT | なし（4ms） |
| REPEATABLE READ | **トランザクション終了まで待つ**（6 秒） |
| SERIALIZABLE / `HOLDLOCK` | **トランザクション終了まで待つ**（6 秒） |

REPEATABLE READ 以上や `HOLDLOCK` は、読んだ制御テーブルの行に S ロックをトランザクション終了まで持ち続けます。このため、UPDATE がそれを待ちます。これは旧ビューでも同じです。
切替の UPDATE には `SET LOCK_TIMEOUT` を付け、待ちが長い場合は再試行するのが安全です。

## 7. 推定行数・統計

- 新ビューでは、制御テーブルの判定による推定行数の減少がありません。各側の推定値は、そのテーブルの統計どおりでした。切替後に制御テーブルの統計が古いままでも、公開中の側が過小に見積もられることはありませんでした。
- 非公開側にデータがある間は、推定行数が実際の約 2 倍（両側の合計）になります。メモリ付与が多めになる程度で、結果や待ちへの影響はありません。後片付けで空になれば元に戻ります。
- 投入後の最初のクエリでは、統計の自動更新と再コンパイルが行われ、新しい行数で実行計画が作り直されていました。大きなテーブルでは、最初に実行した利用者のクエリが統計更新の時間を待つことになります。**投入後・切替前に、非公開側へ `UPDATE STATISTICS` を実行しておくこと**を推奨します（30 万行で 130ms。読み取り中でも待ちません）。

## 8. 非クラスタ化インデックスとログ量

空のテーブルへ `INSERT … WITH (TABLOCK)` で 30 万行（約 158MB）を投入したときのログ量です。

| 投入先 | ログ量 |
| --- | --- |
| 主キー（クラスタ化）のみ | 0.5MB |
| 主キー + 非クラスタ化インデックス 1 本 | 15.7MB |

- 非クラスタ化インデックスへの書き込みは最小ログになりませんが、DELETE で空にする方式（30 万行で約 280MB）と比べれば十分に小さい量です。
- 投入前にインデックスを削除し、投入後に作り直す方法はとりません。インデックスの作成は Sch-M などの強いロックが必要で、ビューを読んでいる SELECT とぶつかります。また SWITCH の条件として、A・B・退避用のインデックスを常にそろえておく必要があります。

## 9. 本番に向けた確認事項

1. 公開ビューを `NOLOCK` や REPEATABLE READ 以上で読む利用者がいないか確認する。
2. 本番の代表的なクエリについて、検証サーバーで実行計画（Seek か、非公開側の Executes が 0 か）を確認する。
3. 索引のない列で並べ替えるクエリがよく使われるなら、インデックスの追加を検討する。
4. 全件更新の手順に「投入後・切替前に `UPDATE STATISTICS`」を入れる。
5. 切替の UPDATE に `LOCK_TIMEOUT` と再試行を入れる。
